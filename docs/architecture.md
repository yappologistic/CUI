## The shape of a frame

CUI is immediate mode: the app describes its whole interface every frame, and CUI works out what changed. One frame goes like this.

1. **`cui_begin_frame`** (`cui_core.c`) advances time, resets the frame arena, swaps last frame's hit list and focus order into place, and works out what the pointer is over.
2. **The app's code runs.** Each component call (`cui_button`, `cui_row`, `cui_data_grid_begin`...) does three things at once:
   - reads input against **last frame's** rectangles (`cui__interact`), so a click lands on what the user saw;
   - reads and updates its **persistent state** (`cui_state`), keyed by its id;
   - adds **nodes** to this frame's layout tree (`cui__node_new`, `cui__open`, `cui__close`), with sizes, colors, text, and optionally a paint callback.
3. **`cui_end_frame`** (`cui_core.c`):
   - `cui__layout` (`cui_layout.c`) measures and places every node, resolves the reading direction, and records each id's rectangle for the next frame;
   - `cui__paint` (`cui_layout.c`) walks the tree and turns it into triangles in the draw list (`cui_draw.c`), calling paint callbacks for anything custom;
   - per-frame input is cleared, unused state is collected (`cui__state_gc`), new glyphs are uploaded.
4. **The renderer** draws the draw list: OpenGL (`src/render/cui_render_gl.c`), CUI's own software rasterizer (`src/render/cui_render_sw.c`), or yours. CUI only emits textured, colored triangles with a few shading modes.
5. **The app loop** (`src/platform/cui_app.c` and one backend file) presents the frame and sleeps until the next event, wakeup or animation frame.

Nothing is retained between frames except what is in `cui_state` and the previous frame's rectangles. That is why components can be plain function calls, and why a component never has to be "removed": when the app stops calling it, its state is collected a few frames later.

## Where things live

```
include/cui/     the public API (cui.h, cui_app.h, cui_render.h, cui_icons.h); everything here is a promise
src/             the library
  cui_internal.h   what more than one source file needs (it starts with a table of contents)
  cui_core.c       context, frame lifecycle, memory, ids and state, interaction and focus
  cui_layout.c     the node tree: building, layout, direction, painting nodes
  cui_draw.c       the draw list and drawing primitives (rects, shadows, text runs)
  cui_text.c       fonts, the glyph atlas, measuring and wrapping text
  cui_theme.c      theme tokens, light and dark, accents, transitions
  cui_*.c          components, one family per file (see below)
  render/          the software and OpenGL renderers
  platform/        the app loop (cui_app.c) and window backends (Win32, Cocoa, X11, SDL2, GLFW)
tests/           unit and interaction tests, render tests, fuzzers, the soak harness, screenshot generators
examples/        apps that use only the public API; the gallery shows every component
docs/            these guides; docs/images is generated by the tests
web/             the WebAssembly build of the docs site
tools/           generators for embedded data (fonts, emoji, bidi and joining tables)
third_party/     vendored stb headers, and Lua 5.4 for the console engine (built only with CUI_LUA=ON)
```

## The core ideas

**Ids.** Every interactive thing has an id, made from its label or id string and the id stack (`cui_make_id`, `cui_push_id`). The id is how a component finds its state and its last rectangle. Two things with the same id in the same scope are a bug; `cui_push_id` around repeated items fixes it.

**State.** `cui_state(ui, id, size)` returns zeroed memory that lives as long as the component keeps being called. It is collected after it goes unused (30 frames for a rectangle only, about five seconds for real data). Anything the state owns (a texture, a buffer) is freed by a function registered with `cui_state_on_free`. Components keep their state in one struct, named after the component (`cui__slider_state`).

**Nodes and layout.** A node is a box: size rules, padding, gap, direction, alignment, colors, an optional text, an optional paint callback. Containers open with `cui__open` and close with `cui__close`. Layout runs once, at the end of the frame, so a component cannot know its own size while it builds; it uses last frame's rectangle (`cui__prev_rect`) when it needs one.

**Frame memory.** `cui__frame_alloc` hands out memory that lives until the next frame starts. Paint data, copies of strings the node will draw, and per-frame scratch go there. It never needs freeing.

**Painting.** Plain boxes, borders and text are painted by the layout pass. Anything else (a chart, a knob, a selection band) sets `node->paint` and `node->paint_data`; the callback runs with the final rectangle and draws with the `cui_draw_*` primitives. Paint callbacks must not change state that the next frame's build depends on, with one exception: recording something only layout knows (the resolved reading direction) for the next frame's input.

**Floating layers.** Popovers, menus, dialogs and tooltips are nodes in their own floating roots, painted after the main tree, with their own hit testing and focus scope.

**Containers being built.** A begin/end component (`cui_table_begin_ex`, `cui_data_grid_begin`, `cui_kanban_begin`...) keeps what its items need in frame memory and points `ui->building.<name>` at it until its `_end`.

## How a component is written

Most components follow the same outline. Keeping to it is what makes a 170-component library readable: once you have read one, you know where to look in the others.

```c
/* one struct for everything that must survive between frames */
typedef struct { float hover, t; bool init; } cui__thing_state;

/* one struct for what the paint callback needs: built in frame memory */
typedef struct { float t, hover; cui_color on; } cui__thing_paint;

static void cui__paint_thing(cui_ctx *ui, cui_node *n, void *data) {
    cui__thing_paint *p = data;
    /* draw inside n->rect with cui_draw_* */
}

bool cui_thing_ex(cui_ctx *ui, const char *id_str, bool *value, const cui_thing_opts *o) {
    cui_thing_opts d;                       /* options: zero means default */
    memset(&d, 0, sizeof d);
    if (!o) o = &d;

    cui_id id = cui_make_id(ui, id_str);
    cui_interact r = cui__interact(ui, id, CUI_IF_FOCUSABLE);   /* 1. input, against last frame */
    cui__thing_state *st = cui_state(ui, id, sizeof *st);        /* 2. state */
    if (r.clicked) *value = !*value;
    cui__tween(ui, &st->t, *value ? 1.0f : 0.0f, CUI__T_STATE);

    int n = cui__node_new(ui, id);                               /* 3. nodes */
    /* sizes, colors from theme tokens (CUI_C), then the paint data */
    cui__thing_paint *p = cui__frame_alloc(ui, sizeof *p);
    p->t = st->t; p->hover = st->hover; p->on = cui__emphasis(ui);
    ui->nodes[n].paint = cui__paint_thing;
    ui->nodes[n].paint_data = p;
    return r.clicked;
}
```

and in `cui.h`, next to its siblings:

```c
typedef struct cui_thing_opts { int _; cui_size width; bool disabled; } cui_thing_opts;
CUI_API bool cui_thing_ex(cui_ctx *ui, const char *id, bool *value, const cui_thing_opts *opts);
#define cui_thing(ui, id, value, ...) cui_thing_ex((ui), (id), (value), CUI__OPTS(cui_thing_opts, __VA_ARGS__))
```

When a component grows past a screen or two, split it by phase rather than by line count: one function for input, one that builds the nodes, one per paint callback, with the values they share in one struct. A reader should be able to find "what happens on a click" or "how it is drawn" without reading the rest.

## Adding a component

1. Put it in the file of its family. A new file is for a new family, not for one component.
2. Declare it in `include/cui/cui.h` next to its siblings: an options struct whose zero value is the default, the `_ex` function, the macro, and a comment that says what it is for.
3. Use what exists: theme tokens through `CUI_C`, the emphasis color through `cui__emphasis`, font sizes through `cui__fs`, motion through the `CUI__T_*` and `CUI__SPRING_*` tokens, the shared pieces in `cui_internal.h`. If you are about to write a small helper, search `cui_internal.h` first; if it is not there and a second file needs it, put it there.
4. Support the keyboard, a reduced motion path, light and dark, phone width, and right to left (or keep it left to right with `cui__keep_ltr` if it shows code, numbers or a hand-drawn grid).
5. Add it to the gallery (`examples/gallery_ui.c` or `gallery_more.c`), give it a scene in `tests/component_shots.c`, document it in `docs/components.md` or `docs/components-more.md`, and add tests for its behavior in `tests/test_main.c`.
6. Add a line to `CHANGELOG.md`.

## Changing code safely

- **Tests:** `ctest` runs the unit and interaction tests, the render tests, the fuzzers and a short soak run. Run it with text shaping off and on (`-DCUI_TEXT_SHAPING=ON`) and under the sanitizers before a pull request.
- **Screenshots:** `cui_screenshots` and `cui_component_shots` render every gallery page and component. For a change that should not look different, render before and after and compare the files byte for byte.
- **Behavior fingerprint:** `tests/soak.c` drives an app with seeded input at a fixed time step, so runs are deterministic. With `--hash` it prints a fingerprint of every frame's draw data. A refactor that keeps behavior keeps the fingerprint; build an app against the old and the new library and compare:

  ```sh
  cc -O1 -DCUI_SOAK_NO_X11 -DSOAK_APP='"../examples/mail.c"' -I include -I src tests/soak.c build/libcui.a -lm -lpthread -ldl -o soak-mail
  ./soak-mail --minutes 2 --seed 5 --hash
  ```

  The harness only reaches what the app shows. For a component that no example uses, write a small app that shows it (a `main` that calls `cui_app_run`, in a few variants: narrow, read only, empty), build it with `-DSOAK_APP='"path/to/app.c"'` against both libraries and compare several seeds. Each library must be built with its own headers. To check that the run reaches the code you changed, break that code on purpose once: the fingerprint should change.

- **Phases:** when you split a long function, keep every `cui__interact`, `cui_state` and node call in the same order. Order is behavior: it decides ids, hit testing and state lifetimes. Name the struct the phases share after the component (`cui__tle_frame` for the timeline editor) and keep the original function as a short driver that reads top to bottom: setup, input, build, result.

- **Size:** check what a change adds to `examples/hello` in a `MinSizeRel` build. The core must not call into a component's file directly (Windows linkers keep whole files), so optional parts are reached through hooks they install themselves (see `ui->emoji_hook`).

## Rules that keep it fast and small

- A frame where nothing changed allocates nothing: use frame memory for per-frame data and `cui_state` for what persists.
- Nothing animates or polls unless it has to: what waits asks for a wakeup (`cui__wakeup_after` in components, `cui_request_wakeup` in apps) instead of redrawing every frame.
- Long lists build only the rows in view (`cui_virtual_list_begin`, the data grid, the terminal, the emoji grid).
- The software renderer redraws only tiles that changed, so a component must draw the same triangles for the same state: no randomness or time in paint callbacks unless the component is animating.
- [Performance](performance.md) describes how this is measured, with the soak harness, over hours of use.
